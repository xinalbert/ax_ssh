## 2026-09-01 修复 worker 关闭阻塞与 SFTP 上传内存峰值

- 触发原因：SSH、Telnet、Serial 的关闭路径在有界命令队列满时等待异步 `send`，可能绕过后续固定超时；SFTP 本地上传在 application bridge 先将最大 512 MiB 文件完整读入内存。
- 执行内容：三类 worker 关闭改为非阻塞 `try_send(Disconnect)`，队列满时直接进入既有 join/abort 超时；应用退出改为并发回收并设置五秒总时限；SFTP 上传请求改为只携带本地路径和预检大小，worker 通过单个 64 KiB blocking 读取任务逐块校验、上传和发布，并用进程级 8 路 semaphore 限制同时上传；增加满队列、永久 I/O 任务强制中止及源文件变化/分块读取回归测试。
- 影响文件：`src/app.rs`、`src/{ssh/worker,telnet,serial}.rs`、`src/sftp/transfer.rs`、`src/app/{sftp_bridge.rs,state/terminal.rs}`、双语架构文档。
- 验证结果：`cargo fmt --all -- --check`、`cargo check --locked --offline`、严格 Clippy、完整 `cargo test --locked --offline`（库 223、应用 212、Doc tests 0）和 `git diff --check` 通过；真实断网/设备拔出和多路大文件压力仍需目标平台验收。
- 边界：不改变 SSH host-key trust、凭据生命周期、SFTP 原子临时发布或每 Tab 两路 transfer 上限；编辑器的 `WriteText` 仍使用独立的 4 MiB 文本编辑上限。

- 执行内容：在终端领域模型读取 `APP_KEYPAD`，新增 UI 无关的 `TerminalKeypadKey` 与 DEC/xterm SS3 编码；已显示 Winit 窗口在无修饰、非合成的物理小键盘按下时检查活动 terminal 的 application-keypad 模式，命中后复用现有的窗口路由、模态锁定、连接、worker 和状态错误处理，并阻止重复进入 Slint 文本代理。普通模式、NumLock、IME 与带修饰键的小键盘仍由 Slint 处理。
- 影响文件：`src/{terminal,terminal/input,terminal/model,terminal/tests}.rs`、`src/app/{input,terminal_bridge,diagnostics,window_bridge}.rs`、`docs/{architecture,architecture.zh}.md`、tracker current/project-map。
- 计划状态变更：KPAD1: pending -> completed；KPAD2: pending -> completed
- 验证结果：application-keypad 编码、终端模式和物理 key code 定向回归，以及 `cargo fmt --all -- --check`、`cargo check --locked --offline`、严格 Clippy、完整 `cargo test --locked --offline` 和 `git diff --check` 通过。macOS 直接 Windows target check 因缺少 Windows SDK headers 失败；`cargo xwin` 会下载未缓存的 Skia 产物，已停止，未将联网下载纳入离线验证。Windows CI/目标机编译和物理键盘实机验收仍待执行。
